1LLM 极简均衡测试集

目标：用极少题量快速摸底不同供应商模型的「中文知识 + 数理逻辑」上限，省调用成本与时间。

选型：一文一理的黄金组合

  • CMMLU：67 个中国本土学科，测中文知识广度。
  • HumanEvalPlus：在 HumanEval 上加数万严苛用例，测硬核编程逻辑，沙盒一跑漏洞原形毕露。

核心策略：按学科分层截断

  • EvalScope 原生后端把 CMMLU 拆成 67 个学科子集，--limit 对每个子集单独截断 → 天然分层均衡。
  • 每科取 50 题 → 3350 题；固定随机种子可复现，零文件操作，学科权重完美保留。
  • HumanEvalPlus 仅 164 题、成本极低，保持全量，并开 Docker 沙盒安全执行生成代码。

2VLM 分层抽样测试集

目标：把 1000~2700 题的多模态测试集压到 ~500 题，且能力分布与原集一致。

核心痛点与解法

  • 痛点：测试集按类别集中排序，框架的 limit 是「全局前 N 条」→ 可能某些类别一题没抽到，维度失衡。
  • 解法：读本地 TSV，按类别列（如能力类别 / 任务类型 / 场景，自动探测）做等比例分层抽样（固定随机种子），存回原文件名喂给框架。
  • 可复现：任何机器抽到完全相同的 ~500 题；自动备份全量，避免反复抽样越缩越小。

两种跑法：分层微缩 vs. 全量

  • 分层微缩（默认）：每个集压到 ~500 题，4 个集一起跑，快速画「能力雷达图」做横向对比。
  • 单个/少数几个数据集全量：只关心某一两个能力时，跳过抽样、直接对选中的集跑全量（不设 limit）——题量虽大但维度最完整，适合定点深测某能力或复核微缩版结论。
两种跑法共用同一运行器：抽样只是「跑前对 TSV 的预处理」，要全量就不做抽样这一步、直接跑原始数据集即可，命令本身不变。

3单轮长文本性能压测

目标：横向对比商业 API 的长上下文推理性能，核心看首字延迟 TTFT 与 生成速度 TPOT。

三大公平性设计

  • 数据集用 longalpaca：真实长文本（>6000 tok）。不用 random——乱码会让模型立刻 EOS，TPOT 失真。
  • 防服务端缓存作弊：并发梯队间游标自增不重复；用偏移量错开历史，杜绝 KV/Prefix Cache 命中污染 TTFT。
  • 对齐生成长度：商业 API 不支持忽略结束符，用统一的最大输出 token 截断天花板，保证 TPOT 可比。

压测梯队设计

  • 并发梯队 1 / 8 / 16：分别测单点极限速度、并发吞吐、极限吞吐；各梯队对应请求量 20 / 80 / 160。
  • 流式必开：才能精确捕获 TTFT。预热 2 条：暖机排除冷启动，不计入报告。
  • 全程发约 262 条互不重复的请求；预热数据也来自数据集并消耗游标 → 全是新鲜语料，彻底杜绝缓存作弊。

关键指标（对比时只看归一化值）

指标含义
TTFT首字延迟，衡量长 Prompt 的 Prefill 速度（看 P50 / P99）
TPOT(总延迟−TTFT) / 输出 token，剔除输出长短影响，最公平的生成速度
RPS / TPS高并发下的吞吐与算力水位
绝不直接对比总 Latency——它受各模型话术长短影响极大。看平均输出 token 是否都在 500 左右，确认截断已生效、对比基础公平。

执行策略：一键脚本 + 厂商命名防撞

  • 一条命令跑完：python scripts/perf/run_longalpaca_bench.py <模型>-<厂商>。所有保证公平的参数（数据集 / 梯队 / 截断 / 流式 / 预热）都锁死在脚本的 FIXED 里，API Key 走环境变量、绝不硬编码。
  • profile = 模型 × 厂商：同一款模型常在多家厂商都有（如 deepseek-v3.2 既在阿里百炼又在腾讯云），故 profile 用 <模型>-<厂商> 双维度登记。
  • 输出命名带厂商：结果落在 results/longalpaca/<时间戳>/longalpaca_<模型>-<厂商>/，内含 perf_report.html、benchmark.log 及各并发档的 benchmark_data.db。
为什么 --name 必须带厂商：输出路径只到「秒」级时间戳，若只带模型名，同款模型跨厂商并发跑会算出同一目录而撞车——evalscope 发现 benchmark_data.db 已存在会直接退出。带上厂商即保证（厂商,模型）维度唯一，同秒并发也不冲突。

定时自动化 + 智能体归档

  • 智能体一次搭建、自动跑：把一段「搭建提示词」发给本地定时调度智能体（hermes），它便自行创建 3 个每日重复任务——21:00 / 04:00 / 15:00，到点各跑一轮（由智能体的调度机制触发，而非在代码里写死等待），时间戳天然隔离、互不覆盖。
  • 每个时段用不同 offset：21 点档 500 / 凌晨 4 点档 1000 / 15 点档 1500（每轮消耗 262 条，间隔 500 互不重叠），三档各打全新语料，三次之间彻底不蹭彼此残留的服务端缓存。同档跨天用同一 offset，方便看「同一时段的日间趋势」。
  • 到点自动整理归档：每次跑完自动定位最新结果目录，按 parallel=1 / 8 / 16 三档提取 TTFT、TPOT（均看 P50 / P99）、RPS、TPS，连同成功 / 失败数沉淀成 notes/perf-commercial-apis/runs/<日期>_<时间>_<profile>.md，并在执行回执里贴表点评是否异常。
前置：API Key 须设为持久环境变量（DASHSCOPE_API_KEY，腾讯另需 TENCENT_API_KEY），否则定时任务到点取不到 key 会直接退出。
搭建提示词存档于 notes/perf-commercial-apis/scheduled_agent_prompt.md：一次性发给 hermes 即自动建好三个任务；也可自己手动跑脚本，只是少了那步自动归档与点评。

4多轮对话 KV 缓存命中率压测

目标：评估服务端在多轮对话中对历史上下文（Prefix Cache）的复用能力——多轮又快又省的关键。

两个核心指标

指标口径意义
Cache Hit (%)命中 token ÷ 全部输入 token，按 token 总量加权（含第 1 轮 0%）实际省了多少钱 / 算力
Eligible Cache Hit Rate剔除第 1 轮与本轮新内容后的命中率服务端缓存系统做得有多好
黄金判真伪：Eligible 死磕 100.00 = 服务端没回传，客户端理论估算；跑出 93.00 等非整数 = 走真实命中数据。

三大对齐机制（跨厂商绝对公平）

  • 数据集预生成：脚本一次跑出固定的多轮对话（基于 swe_smith，「长首轮 + 尾部增量」纺锤形，最贴 Agent 场景），随机性冻结在文件里，所有厂商吃同一份。
  • 会话隔离：腾讯云需开会话缓存开关、自动注入会话标识；阿里百炼隐式缓存、无需此参数。
  • 防复测污染：同模型同厂商重测，用大池子 + 偏移量取不相交子集，避免残留缓存让冷启动虚高。
统一原则：控制变量 · 绝对公平 · 可复现。能力评测追求「分层均衡 + 低成本摸底」，性能压测追求「杜绝缓存作弊 + 归一化指标」。
