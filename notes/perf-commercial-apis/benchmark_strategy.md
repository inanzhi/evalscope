# 商业闭源大模型性能基准测试方案 (单轮长文本)

## 1. 测试背景与目标
本方案旨在提供一套绝对公平的基准测试（Benchmark）策略，用于横向对比不同商业大模型 API（如阿里云百炼、腾讯云等）的单轮推理性能。
测试的核心场景为**长上下文（Long Context）**处理能力，核心观测指标为**首字延迟（TTFT）**和**生成速度（TPOT）**。

## 2. 核心压测策略设计

### 2.1 数据集选择：`longalpaca`
* **不使用 `random` 数据集的原因**：`random` 会生成无意义的乱码 Token，商业模型遇到乱码通常会立刻输出 1~3 个 Token 并触发 EOS（结束符）停止生成。这会导致 TPOT 失真，无法衡量真实的生成性能。
* **选择 `longalpaca`**：自动拉取 `LongAlpaca-12k` 真实长文本语料（通常 > 6000 tokens），让模型进行正常的语义理解和较长的文本输出。

### 2.2 防护机制：避免服务端缓存“作弊”
* **内部游标自增**：在同一次压测中执行多个并发梯队时（如并发 1 -> 8 -> 16），框架会自动推进数据游标，绝不重复提问同一道题。
* **`--dataset-offset`**：手动指定游标初始偏移量。不同轮次的压测（或不同模型的压测）指定不同的 offset，可以彻底杜绝服务端底层 KV-Cache / Prefix Cache 命中，保证 TTFT 反映的是真实的第一次计算耗时。

### 2.3 强制对齐生成长度：`--max-tokens`
因为商业 API 通常不支持 `{"ignore_eos": true}`，模型输出长度会自然波动。我们通过 `--max-tokens 512` 设置强制截断的天花板，防止某些模型无限输出消耗成本，同时将所有模型的输出量级拉齐，保证 TPOT 比较的公平性。

## 3. 具体测试命令与参数详解

```bash
evalscope perf \
  --url https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions \
  --api-key "YOUR_API_KEY" \
  --model <待测模型名称> \
  --dataset longalpaca \
  --dataset-offset 500 \
  --max-tokens 512 \
  --parallel 1 8 16 \
  --number 20 80 160 \
  --stream \
  --warmup-num 2 \
  --read-timeout 300 \
  --name "longalpaca_<模型>_<厂商>"
```

### 参数详细解析
* `--url / --api-key / --model`：商业 API 的标准调用凭证和目标模型名。
* `--dataset longalpaca`：使用长文本数据集进行评测。
* `--dataset-offset 500`：**跳过数据集前 500 条数据**，从第 501 条开始压测，确保测试语料和之前跑过的实验完全不重复。
* `--max-tokens 512`：强制模型在输出 512 个 token 后截断停止。
* `--parallel 1 8 16`：并发梯队。按顺序分别执行：单线程（测单点极限速度）、8线程、16线程（测并发吞吐）。
* `--number 20 80 160`：各梯队对应的总请求量。并发 1 发 20 条，并发 8 发 80 条，并发 16 发 160 条。同一次命令中梯队间的数据也不会重复。
* `--stream`：**必须开启**。开启流式传输才能精确捕获到首字返回时间（TTFT）。该参数为开关型（`argparse.BooleanOptionalAction`），写 `--stream` 即开启、`--no-stream` 关闭
* `--warmup-num 2`：预热机制。正式压测前先发 2 条请求“暖机”，建立网络连接并排除初次分配资源的冷启动延迟，这部分数据不计入最终报告。
* `--read-timeout 300`：单次请求读超时 300s。长上下文 prefill 较慢，给足余量避免误判超时（perf 默认 total-timeout 6h，这里收紧到 300s 更早发现卡死）。perf 不自动重试，超时即计为失败。
* `--name "longalpaca_<模型>_<厂商>"`：结果库名 / 输出子目录名。**务必把模型名和厂商名都带上**。输出路径是 `<outputs-dir>/<时间戳>/<name>/...`，时间戳只到秒；如果只写模型名，**同一款模型在不同厂商并发跑**（如 deepseek-v3.2 同时打腾讯云和阿里百炼）会算出同一目录而撞车——evalscope 发现 `benchmark_data.db` 已存在会直接退出。带上厂商名（如 `longalpaca_deepseek-v3.2_bailian` / `longalpaca_deepseek-v3.2_tencent`）即可保证 (厂商,模型) 维度唯一，哪怕同一秒并发也不冲突。

### 💡 进阶理解：框架到底发了多少条请求？（压测执行时间线拆解）
以上述命令的配置为例（`--dataset-offset 500`，`--warmup-num 2`，`--parallel 1 8 16`，`--number 20 80 160`），框架底层的执行动作和取数逻辑如下：

总计会向 API 发送 **262 条** 独立且互不重复的长文本请求（`2 + 20 + 80 + 160 = 262`）。

1. **阶段 0：预热阶段 (Warmup)**
   * **取数据**：系统从 `longalpaca` 数据集跳过前 500 条后，取出 **第 500 题** 和 **第 501 题**。
   * **怎么发**：按照将要进行的第一个梯队的并发数（即 `parallel=1`），单线程将这 2 题依次发给模型。
   * **结果怎么算**：这两题的耗时（TTFT、TPOT）**直接丢弃，不计入报告**。纯粹用于激活服务端网络和显存池。
2. **阶段 1：并发 1 测试**
   * **取数据**：游标顺延，取出 **第 502 题 ~ 第 521 题**（共 20 题）。
   * **怎么发**：保持单线程发包。
   * **结果怎么算**：数据被精准记录，生成报告中 `Parallel=1` 这一行的单点极限性能指标。
3. **阶段 2：并发 8 测试**
   * **取数据**：游标顺延，取出 **第 522 题 ~ 第 601 题**（共 80 题）。
   * **怎么发**：拉起 8 个并发线程，将这 80 题并发发出。
   * **结果怎么算**：生成报告中 `Parallel=8` 这一行的并发指标。
4. **阶段 3：并发 16 测试**
   * **取数据**：游标顺延，取出 **第 602 题 ~ 第 761 题**（共 160 题）。
   * **怎么发**：拉起 16 个并发线程满载测试。
   * **结果怎么算**：生成报告中 `Parallel=16` 这一行的极限吞吐指标。

> **核心总结**：预热数据**来源于数据集**，且会**真实消耗掉抽取名额（游标向后顺延）**。这完美保证了整场压测中，即使分为多个阶段，发给模型的也全是新鲜语料，彻底杜绝了模型底层缓存（KV-Cache）作弊造成的指标污染。

## 4. 报告方式与字段含义

命令执行完毕后，EvalScope 会在终端直接输出一张 Markdown 格式的统计表格（同时也会通过你配置的 `--name` 写入本地的 SQLite 数据库或云端看板）。
由于各商业模型的实际输出长度即使设置了天花板也可能存在微小差异，**绝对不能直接对比总 Latency**，而应重点参考已经通过数学公式归一化的 **TTFT** 和 **TPOT**。

### 核心字段含义（做模型对比时重点关注）

| 指标字段 | 全称 | 含义与价值 |
| --- | --- | --- |
| **TTFT** | Time To First Token | **首字延迟**。表示从发请求到收到第 1 个 token 的时间。主要衡量长上下文输入的 Prompt 处理速度（Prefill 计算阶段）。<br>*（重点关注 P50、P99 以评估响应稳定度）* |
| **TPOT** | Time Per Output Token | **单个输出 Token 耗时**。公式：`(总延迟 - TTFT) / 输出 Token 数`。完全剔除了输出长短不同的影响，是衡量纯生成速度（Decode 阶段）的最核心、最公平的指标。<br>*（重点关注 P50、P99 以评估生成流畅度）* |
| **RPS** | Requests Per Second | **每秒请求数**。吞吐量指标，在 `--parallel 16` 这种高并发测试下，衡量服务端的并发承载力上限。 |
| **TPS** | Tokens Per Second | **每秒 Token 数**。吞吐量指标，结合并发数，反映服务端整体的生成算力水位。 |

### 辅助观测字段

| 指标字段 | 含义 | 观测价值 |
| --- | --- | --- |
| **Latency** | 端到端总延迟 | **不推荐跨模型直接对比**，因为它受各个模型生成的最终话术长短影响极大。 |
| **Prompt Tokens** | 输入 Token 均值 | 用来验证数据集抽样的稳定性，对于 `longalpaca`，这个值应该稳定在数千 tokens。 |
| **Completion Tokens** | 输出 Token 均值 | 如果各模型测出来的这个均值都在 500 左右，说明你的 `--max-tokens` 已经成功生效，对比的基础是公平的。 |
